== What low level design means

High level design decides which services exist and how they talk to each other.
Low level design zooms in on a single service and decides how its code is organised: which classes exist, what each one is responsible for, and how they depend on one another.

A good low level design is not the one with the most patterns.
It is the one where a new requirement touches as few classes as possible, and where each change is easy to test in isolation.

== From requirements to design

Knowing principles and patterns is necessary but not sufficient.
A sound design comes from applying them in a deliberate order, whether the problem is a parking lot, a vending machine, a file search tool or a feature in a production service:

. *Clarify requirements.* Establish what the system must do, what is out of scope, and whether several users or threads use it at once. Write the agreed list down.
. *Find the core entities.* The nouns in the requirements are candidate classes. Each one gets a single responsibility.
. *Define relationships.* Decide what *is a* kind of what, and what *has a* what. A quick class diagram keeps everyone working on the design aligned.
. *Write the public API first.* Method signatures for the main use cases come before any implementation.
. *Apply patterns only where the problem calls for them.* Each pattern must name the part of the design that varies and what it costs.
. *Build the core flow.* A working main path with sensible validation and errors is worth more than a large, unfinished class diagram.
. *Handle concurrency.* Identify the shared state, such as a parking spot two cars try to take at once, and decide how it is protected.
. *Test the design with an extension.* Ask "how would a new requirement be added?". A good design answers with a new class rather than edits to existing ones.

A design is not measured by how many patterns it uses.
It is measured by whether it is correct, easy to extend and safe under concurrency, and whether every trade-off in it has a clear reason.

== Why principles and not rules

None of these principles is a law.
Each one trades something away: an extra interface costs indirection, removing duplication costs coupling.
The skill in low level design is knowing which trade-off fits the problem at hand, and the articles call out where each principle stops helping.
