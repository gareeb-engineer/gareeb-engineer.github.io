Low Level Design

How to shape classes, interfaces and their relationships so code stays easy to change.

  • Low Level Design
  • Java
  • Object-Oriented Design
~2 min read Updated Oct 27, 2026

What low level design means

High level design decides which services exist and how they talk to each other. Low level design zooms in on a single service and decides how its code is organised: which classes exist, what each one is responsible for, and how they depend on one another.

A good low level design is not the one with the most patterns. It is the one where a new requirement touches as few classes as possible, and where each change is easy to test in isolation.

How to read this series

Start with the general design principles. They are short rules of thumb that apply to any code, object-oriented or not. Then move on to SOLID, five principles that are specific to object-oriented design and build directly on those ideas.

  • Design Principles — DRY, KISS, YAGNI, the Law of Demeter, and the three Gang of Four principles: composition over inheritance, programming to an interface, and encapsulating what varies.

  • SOLID Principles — single responsibility, open/closed, Liskov substitution, interface segregation and dependency inversion.

  • Gang of Four Design Patterns — the twelve most useful patterns, how to tell similar ones apart, and which patterns fit common design problems.

From requirements to design

Knowing principles and patterns is necessary but not sufficient. A sound design comes from applying them in a deliberate order, whether the problem is a parking lot, a vending machine, a file search tool or a feature in a production service:

  1. Clarify requirements. Establish what the system must do, what is out of scope, and whether several users or threads use it at once. Write the agreed list down.

  2. Find the core entities. The nouns in the requirements are candidate classes. Each one gets a single responsibility.

  3. Define relationships. Decide what is a kind of what, and what has a what. A quick class diagram keeps everyone working on the design aligned.

  4. Write the public API first. Method signatures for the main use cases come before any implementation.

  5. Apply patterns only where the problem calls for them. Each pattern must name the part of the design that varies and what it costs.

  6. Build the core flow. A working main path with sensible validation and errors is worth more than a large, unfinished class diagram.

  7. Handle concurrency. Identify the shared state, such as a parking spot two cars try to take at once, and decide how it is protected.

  8. Test the design with an extension. Ask "how would a new requirement be added?". A good design answers with a new class rather than edits to existing ones.

A design is not measured by how many patterns it uses. It is measured by whether it is correct, easy to extend and safe under concurrency, and whether every trade-off in it has a clear reason.

Why principles and not rules

None of these principles is a law. Each one trades something away: an extra interface costs indirection, removing duplication costs coupling. The skill in low level design is knowing which trade-off fits the problem at hand, and the articles call out where each principle stops helping.
