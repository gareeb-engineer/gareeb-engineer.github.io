SOLID Principles

Five object-oriented design principles, each with the warning signs and a before and after Java example.

  • Medium
  • Low Level Design
  • SOLID
  • Java
~4 min read Updated Oct 27, 2026

SOLID is an acronym for five principles collected by Robert C. Martin; the acronym itself was coined by Michael Feathers. Together they aim at one outcome: when requirements change, a small piece of code is added or swapped instead of many existing classes being edited.

Each section below explains the principle, lists the warning signs that it is being broken, and shows a small Java example before and after.

S: Single Responsibility Principle

A class should have only one reason to change. "Responsibility" here means a source of change, usually one person or team who asks for it. If the finance team and the operations team can both request edits to the same class for unrelated reasons, it has two responsibilities.

Warning signs:

  • The class name contains "And", "Manager" or "Util", and its methods have little in common.

  • Unrelated tests break when one feature changes.

  • The class imports database, formatting and network libraries at the same time.

Before: calculation, formatting and storage in one class
class Invoice {
    private final List<LineItem> items;

    Invoice(List<LineItem> items) { this.items = items; }

    BigDecimal total() {
        return items.stream().map(LineItem::amount).reduce(BigDecimal.ZERO, BigDecimal::add);
    }

    String toPdfText() { /* layout and fonts */ return "..."; }

    void saveToDatabase(Connection connection) { /* SQL insert */ }
}
After: one reason to change per class
class Invoice {
    private final List<LineItem> items;

    Invoice(List<LineItem> items) { this.items = List.copyOf(items); }

    BigDecimal total() {
        return items.stream().map(LineItem::amount).reduce(BigDecimal.ZERO, BigDecimal::add);
    }
}

class InvoicePdfRenderer {
    byte[] render(Invoice invoice) { /* layout and fonts */ return new byte[0]; }
}

interface InvoiceRepository {
    void save(Invoice invoice);
}

A change to the PDF layout now touches only the renderer, and the total can be tested without a database.

O: Open/Closed Principle

Software should be open for extension but closed for modification. When a new variant arrives, it is added as a new class rather than by editing a working one. Editing tested code for every new case is how regressions creep in.

Warning signs:

  • A switch or if-else chain on a type code appears in several places.

  • Adding a new kind of thing means searching the codebase for every place to update.

Before: every new customer type edits this method
class DiscountCalculator {
    BigDecimal discount(Customer customer, BigDecimal amount) {
        switch (customer.type()) {
            case REGULAR:  return BigDecimal.ZERO;
            case PREMIUM:  return amount.multiply(new BigDecimal("0.10"));
            case EMPLOYEE: return amount.multiply(new BigDecimal("0.30"));
            default: throw new IllegalStateException("Unknown type");
        }
    }
}
After: new policies are new classes
interface DiscountPolicy {
    BigDecimal discount(BigDecimal amount);
}

class NoDiscount implements DiscountPolicy {
    public BigDecimal discount(BigDecimal amount) { return BigDecimal.ZERO; }
}

class PercentageDiscount implements DiscountPolicy {
    private final BigDecimal rate;

    PercentageDiscount(String rate) { this.rate = new BigDecimal(rate); }

    public BigDecimal discount(BigDecimal amount) { return amount.multiply(rate); }
}

// Wiring decides which policy a customer gets; the calculation code never changes.
DiscountPolicy premium = new PercentageDiscount("0.10");
Apply the open/closed principle where variation has actually happened. One switch with two stable cases is fine. YAGNI still applies.

L: Liskov Substitution Principle

Objects of a subtype must be usable anywhere the parent type is expected, without the caller noticing. A subclass may add behaviour, but it must not weaken what the parent promises or demand more than the parent required.

More precisely, a subtype must follow four rules. Together they are the full meaning of the principle:

  • No stronger preconditions. It must accept every input the parent accepts. A subclass that rejects negative numbers the parent allowed breaks callers.

  • No weaker postconditions. It must deliver everything the parent promises. The Square below breaks this: setWidth promises the height stays the same.

  • Keep the invariants. Whatever is always true of the parent, such as "the balance is never negative", must stay true.

  • No surprising exceptions. It must not throw kinds of exceptions that callers of the parent are not prepared for.

Warning signs:

  • A subclass overrides a method to throw UnsupportedOperationException.

  • Callers check instanceof before calling a method, to avoid a subclass that behaves differently.

The classic example is a square that extends a rectangle. Mathematically a square is a rectangle, but a mutable Square cannot keep the promise that setting the width leaves the height unchanged.

Before: Square breaks the Rectangle contract
class Rectangle {
    protected int width, height;
    void setWidth(int width)   { this.width = width; }
    void setHeight(int height) { this.height = height; }
    int area() { return width * height; }
}

class Square extends Rectangle {
    @Override void setWidth(int width)   { this.width = width; this.height = width; }
    @Override void setHeight(int height) { this.width = height; this.height = height; }
}

void resize(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20; // fails for a Square: area is 16
}
After: model the shared behaviour, not the inheritance
interface Shape {
    int area();
}

record Rectangle(int width, int height) implements Shape {
    public int area() { return width * height; }
}

record Square(int side) implements Shape {
    public int area() { return side * side; }
}

The fix is not "never use inheritance". It is to make sure the parent’s contract is something every subtype can honour.

I: Interface Segregation Principle

No client should be forced to depend on methods it does not use. Large interfaces push implementers into empty or throwing methods, and every change to the interface ripples into classes that never cared about it.

Warning signs:

  • Implementations full of empty methods or UnsupportedOperationException.

  • An interface change forces unrelated modules to be recompiled or redeployed.

Before: one interface for every device
interface OfficeMachine {
    void print(Document document);
    void scan(Document document);
    void fax(Document document);
}

class BasicPrinter implements OfficeMachine {
    public void print(Document document) { /* prints */ }
    public void scan(Document document) { throw new UnsupportedOperationException(); }
    public void fax(Document document)  { throw new UnsupportedOperationException(); }
}
After: small interfaces, combined where needed
interface Printer { void print(Document document); }
interface Scanner { void scan(Document document); }
interface Fax     { void fax(Document document); }

class BasicPrinter implements Printer {
    public void print(Document document) { /* prints */ }
}

class MultiFunctionDevice implements Printer, Scanner, Fax {
    public void print(Document document) { /* ... */ }
    public void scan(Document document)  { /* ... */ }
    public void fax(Document document)   { /* ... */ }
}

Code that only prints now depends on Printer alone, and a method that throws UnsupportedOperationException is often a Liskov substitution problem as well.

D: Dependency Inversion Principle

High-level business logic should not depend on low-level details such as databases, frameworks or HTTP clients. Both should depend on an abstraction, and that abstraction should be owned by the business side. The dependency "inverts" because the detail now implements an interface that the high-level code defines.

Warning signs:

  • Business classes create their own collaborators with new for databases, clients or clocks.

  • Unit tests need a real database or network because nothing can be swapped out.

Before: the service is welded to MySQL
class OrderService {
    private final MySqlOrderRepository repository = new MySqlOrderRepository();

    void place(Order order) {
        order.validate();
        repository.insert(order);
    }
}
After: the service owns the abstraction; the detail is injected
interface OrderRepository {
    void save(Order order);
}

class OrderService {
    private final OrderRepository repository;

    OrderService(OrderRepository repository) { this.repository = repository; }

    void place(Order order) {
        order.validate();
        repository.save(order);
    }
}

class MySqlOrderRepository implements OrderRepository {
    public void save(Order order) { /* SQL insert */ }
}

// In a test: new OrderService(new InMemoryOrderRepository())
Three terms are often mixed up. Dependency inversion is the principle: depend on abstractions that the business code owns. Inversion of control is the broader idea that something outside a class, a framework or the caller, creates and wires its collaborators. Dependency injection is one technique for both: hand collaborators in, usually through the constructor. Passing the repository through the constructor is enough; a framework such as Spring is optional.

How the five fit together

Principle Question to ask Typical fix

Single responsibility

Who would ask me to change this class?

Split by reason to change

Open/closed

Can I add a variant without editing working code?

Introduce an interface at the point of variation

Liskov substitution

Can every subtype keep the parent’s promises?

Narrow the contract or stop inheriting

Interface segregation

Does each client use every method it depends on?

Split into role interfaces

Dependency inversion

Does business logic know about databases or frameworks?

Depend on an interface the business code owns

The principles reinforce each other. Small, single-purpose classes are easy to put behind small interfaces. Small interfaces are easy to substitute and to inject. Injected dependencies are what allow behaviour to be extended without modifying it. For the general rules underneath all of this, see the design principles article.
