Design Principles

Seven rules of thumb that make everyday code easier to read, test and change, including the core principles of the Gang of Four.

  • Easy
  • Low Level Design
  • Design Principles
  • Java
~5 min read Updated Oct 27, 2026

There are dozens of named design principles. Most of them are restatements of a handful of core ideas, so this article covers only the seven that come up in almost every design discussion and code review.

All of them serve two goals that sit at the centre of every design review. High cohesion means everything inside a class belongs to one job. Low coupling means classes know as little as possible about each other, so a change in one does not ripple into the rest. When two designs compete, the better one raises cohesion or lowers coupling, and that is the reasoning to make explicit when choosing between them.

Three of them come from the Gang of Four: Erich Gamma, Richard Helm, Ralph Johnson and John Vlissides, the authors of Design Patterns: Elements of Reusable Object-Oriented Software (1994). The book states two principles outright, composition over inheritance and programming to an interface, and a third idea, encapsulating what varies, runs through almost every pattern in it. The patterns themselves are covered in Gang of Four Design Patterns.

DRY: Don’t Repeat Yourself

Every piece of knowledge should have a single, authoritative place in the code. When a business rule lives in two places, the two copies eventually drift apart, and one of them becomes a bug.

In the example below, the rule for a valid email address is written twice. When the rule changes, someone has to remember to update both methods.

Before: the same rule in two places
class SignupService {
    void register(String email) {
        if (email == null || !email.contains("@") || email.length() > 254) {
            throw new IllegalArgumentException("Invalid email");
        }
        // ...
    }
}

class ProfileService {
    void changeEmail(String email) {
        if (email == null || !email.contains("@") || email.length() > 254) {
            throw new IllegalArgumentException("Invalid email");
        }
        // ...
    }
}
After: one owner for the rule
final class EmailAddress {
    private final String value;

    EmailAddress(String value) {
        if (value == null || !value.contains("@") || value.length() > 254) {
            throw new IllegalArgumentException("Invalid email");
        }
        this.value = value;
    }

    String value() { return value; }
}
DRY is about duplicated knowledge, not code that happens to look similar. Two blocks that are identical today but change for different reasons should stay separate. Merging them creates coupling, not reuse.

KISS: Keep It Simple

Prefer the simplest design that solves today’s problem. Simple code is faster to read, easier to debug and cheaper to change. Cleverness is usually paid for later by whoever has to maintain it.

A common example is deeply nested conditions. Early returns turn a puzzle into a list of plain checks.

Before: nested conditions
String shippingLabel(Order order) {
    if (order != null) {
        if (order.isPaid()) {
            if (!order.items().isEmpty()) {
                return "Ship to " + order.address();
            } else {
                return "Empty order";
            }
        } else {
            return "Awaiting payment";
        }
    }
    return "No order";
}
After: early returns
String shippingLabel(Order order) {
    if (order == null) return "No order";
    if (!order.isPaid()) return "Awaiting payment";
    if (order.items().isEmpty()) return "Empty order";
    return "Ship to " + order.address();
}

YAGNI: You Aren’t Gonna Need It

Do not build features, extension points or configuration options until a real requirement asks for them. Speculative code still has to be read, tested and maintained, and the future it was built for often never arrives, or arrives in a different shape.

Suppose a report only needs to be exported as CSV. Building a plugin system with a registry, a factory and a configuration file for "future formats" adds three classes and no value. Write the CSV exporter. If a PDF export is requested next quarter, the principles later in this article make it easy to add an interface then, with a real second use case to guide its shape.

YAGNI applies to features, not to quality. Tests, clear names and sensible error handling are not speculative.

Composition over Inheritance

This is the second principle of the Gang of Four: favour object composition over class inheritance.

Inheritance says a class is a kind of its parent. Composition says a class has a collaborator that it delegates to. Composition is the better choice when the goal is only to reuse behaviour, because inheritance exposes every public method of the parent, whether it makes sense or not.

The Java standard library has a well-known example. java.util.Stack extends Vector, so a stack also exposes methods that let callers insert or remove items at any position, which breaks the idea of a stack.

Before: inherits behaviour it should not expose
class BrowserHistory extends java.util.ArrayList<String> {
    void visit(String url) { add(url); }
    String back() { return remove(size() - 1); }
}

// Nothing stops a caller from doing this:
history.add(0, "https://example.com");
history.clear();
After: owns a collection, exposes only what makes sense
class BrowserHistory {
    private final java.util.Deque<String> pages = new java.util.ArrayDeque<>();

    void visit(String url) { pages.push(url); }
    String back() { return pages.pop(); }
    boolean canGoBack() { return !pages.isEmpty(); }
}

Inheritance is still the right tool for a genuine is a relationship where every behaviour of the parent applies to the child. The Liskov substitution principle in the SOLID article gives a precise test for that.

Program to an Interface, not an Implementation

This is the first principle of the Gang of Four.

Depend on what a collaborator can do, not on which concrete class does it. Code written against an interface can be given a different implementation, a fake for tests, or a decorator that adds logging, without changing a single line.

In Java this starts with small habits. Declare variables and parameters with the interface type, and create the concrete type in one place.

Programming to an interface
// Declared as List: any List implementation can be passed in or swapped later.
List<String> names = new ArrayList<>();

interface Notifier {
    void send(String userId, String message);
}

class OrderConfirmation {
    private final Notifier notifier;

    OrderConfirmation(Notifier notifier) { this.notifier = notifier; }

    void confirm(Order order) {
        notifier.send(order.customerId(), "Order " + order.id() + " confirmed");
    }
}

OrderConfirmation works the same with an email, SMS or in-memory notifier. This idea is the foundation of the dependency inversion principle.

Encapsulate What Varies

Find the parts of the code that are likely to change, and separate them from the parts that stay the same. Put each varying part behind its own small class or interface, so a change lands in one place instead of being scattered through stable code.

The Gang of Four describe this as encapsulating the concept that varies, and it is the reason most of their patterns exist. Strategy encapsulates an algorithm, Factory Method encapsulates which class gets created, and Observer encapsulates who needs to be told about a change.

In the example below, tax rules differ by country and change every year, but the checkout flow does not. Mixing them means every tax change edits, and risks breaking, the checkout code.

Before: the varying rule is buried in stable code
class Checkout {
    BigDecimal total(Cart cart, String country) {
        BigDecimal subtotal = cart.subtotal();
        BigDecimal tax;
        if (country.equals("IN")) {
            tax = subtotal.multiply(new BigDecimal("0.18"));
        } else if (country.equals("UK")) {
            tax = subtotal.multiply(new BigDecimal("0.20"));
        } else {
            tax = BigDecimal.ZERO;
        }
        return subtotal.add(tax);
    }
}
After: the varying part has its own home
interface TaxRule {
    BigDecimal taxOn(BigDecimal subtotal);
}

class Checkout {
    private final TaxRule taxRule;

    Checkout(TaxRule taxRule) { this.taxRule = taxRule; }

    BigDecimal total(Cart cart) {
        BigDecimal subtotal = cart.subtotal();
        return subtotal.add(taxRule.taxOn(subtotal));
    }
}

A new country or a rate change is now a new or edited TaxRule, and Checkout is never touched.

Encapsulate only variation that has actually occurred or is a stated requirement. Guessing at future change points is YAGNI in disguise.

Law of Demeter: Talk to Your Friends

A method should only call methods on its own object, its parameters, objects it creates, and its direct fields. It should not reach through one object to get at another object’s internals. Long chains of getters couple the caller to the whole object graph, so a change deep inside it breaks code far away.

Before: reaching through three objects
String city = order.getCustomer().getAddress().getCity();
After: ask the object already at hand
String city = order.shippingCity();

// Inside Order:
String shippingCity() { return customer.shippingCity(); }
The Law of Demeter is not a rule about counting dots. Fluent builders and stream pipelines return new objects at each step, so they do not break it.

Summary

Principle Core idea Watch out for

DRY

One owner for each rule or piece of knowledge

Merging code that only looks alike

KISS

The simplest design that works today

Simple is not the same as short

YAGNI

Build for real requirements only

Skipping tests or error handling in its name

Composition over inheritance (GoF)

Reuse by delegating, not by extending

Forcing composition onto real "is a" relationships

Program to an interface (GoF)

Depend on capabilities, not concrete classes

An interface for every class, with only one implementation forever

Encapsulate what varies (GoF)

Isolate the parts that change from the parts that don’t

Encapsulating changes that are only guesses

Law of Demeter

Talk only to direct collaborators

Wrapper methods that just forward every getter
